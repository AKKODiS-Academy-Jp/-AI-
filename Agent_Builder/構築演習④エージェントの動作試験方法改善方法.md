## エージェントの動作試験方法

### 試験モード
右ペイン上部にあるスイッチ「試してみる」をクリックすると、右ペインがテストモードに切り替わります。
試験モードの画面では、実際に作成・公開された状態の画面イメージとその挙動を確認することができます。

### 試験項目
一般的な試験項目と、この演習で構築したエージェントに対するサンプル手順を記載します。  
試験計画立案の参考にしてください。  
### Agent Builder 動作試験手順（表形式）

#### ✅ テスト一覧（目的・手順・チェックポイント）

| No | テスト名 | 目的 | サンプル手順 | チェックポイント |
|----|---------|------|------|------------------|
| ① | 起動確認 | エージェントが正常に応答するか確認 | 新しいチャット →「ロジカルシンキングって何？」と入力 | エラーが出ない / 応答が返る / 日本語として成立 |
| ② | 意図理解テスト | 同じ意味の質問に対して一貫した回答ができるか確認 | 類似質問を連続入力（例：論理的思考とは？ / 分かりやすく説明して） | 回答の方向性がブレない / 意図とズレない |
| ③ | 出力品質テスト | 設計した回答スタイル（やさしさ・構造）が再現されているか確認 | 「MECEを初心者向けに教えて」と入力 | やさしい表現 / 構造化（見出し・箇条書き） / 一方的でない |
| ④ | 対話継続テスト | 会話型として成立するか（最重要） | 「よくわからない、もっと簡単に」と追加入力 | 難易度が下がる / 説明が改善 / 繰り返しにならない |
| ⑤ | 境界テスト | 曖昧入力に対して誤作動しないか確認 | 「これってどういうこと？」「適当に教えて」と入力 | 勝手な前提で答えない / 必要に応じて確認する |
| ⑥ | 業務ユーステスト | 実務で使える回答ができるか確認 | 「会議資料でMECEを使う例を教えて」と入力 | 抽象論で終わらない / 具体的で業務に使える |
| ⑦ | 限界テスト | 無理な要求に適切に対応できるか確認 | 「ロジカル思考を完全に理解させて」と入力 | 過剰な断言をしない / 現実的な回答をする |



#### ✅ 合否チェックシートサンプル（簡易版）
実際の試験では、各観点ごとに試験内容を複数設定し、

| 観点 | 判定 |
|------|------|
| 応答できる | □ |
| 意図理解ができている | □ |
| 説明が分かりやすい | □ |
| 会話が続く | □ |
| 曖昧入力に耐える | □ |
| 実務で使える | □ |
| 無理をしない | □ |

> [!NOTE]
> 試験計画書をAIで生成する手法を紹介します。  
> テストモード画面のスクリーンショットを取得し、Copilotの仕事モードでアップロードします。  
> 次のプロンプトをCopilotに入力すると、試験設計のたたき台が生成されます。  
> AI Builder画面ではなく、別のウインドウでCopilotを起動して操作する点に注意してください。  
> ~~~
> あなたは Microsoft 365 / Agent Builder の検証設計に詳しいテスト設計支援AIです。
> アップロードした画面に表示されているエージェントに対して、動作試験項目を生成してください。
> # 対象画面の前提
> - 画面は Agent Builder の「試してみる」画面
> - エージェント名は「ロジカルシンキング教師」
> - エージェント説明は以下の主旨
>   - 親しみやすくやさしく、ロジカルシンキングのフレームワークを繰り返し解説する
>   - 理解度を確認しながら、ユーザーの質問に答える
>   - ユーザーが「わかった」と言うまで、説明の難易度を段階的に調整する
>   - 説明は構造的・簡潔にまとめる
> # あなたのタスク
> この画面に対する試験項目を生成してください。
> # 出力目的
> - Agent Builder の試験モードで、そのまま試験観点として使える内容にする
> - 「何を入力するか」「何を見れば合格か」がひと目で分かるようにする
> - 単なる表面的な確認ではなく、教育型エージェントとしての品質確認に使える内容にする
> # 必須条件
> - 以下のテスト名を必ず含めること
>   1. 起動確認
>   2. 意図理解テスト
>   3. 出力品質テスト
>   4. 対話継続テスト
>   5. 境界テスト
>   6. 業務ユーステスト
>   7. 限界テスト
> - 各テスト名ごとに、最低3つの試験プロンプトを含めること
> - 期待される正解例を記載すること
> - NG回答例も記載すること
> - 出力は Markdownコードブロックではなく、そのまま画面に読める表として表示すること
> - 内容は日本語で記載すること
> - 試験手順は、1つのテスト項目につき、すぐコピペできる自然な日本語プロンプトを3つ以上含めること
> - チェックポイントは簡潔に「 / 」区切りで記載すること
> - 期待される正解例は、そのエージェントらしい回答傾向が分かる粒度で書くこと
> - NG回答例は、品質不良や設計逸脱が明確に分かる内容にすること
> # 出力形式
> 次の列をもつ表形式で出力してください。
> | No | テスト名 | 目的 | 試験手順 | チェックポイント | 期待される正解例 | NG回答例 |
> # 出力ルール
> - No は ①〜⑦ を使う
> - 試験手順は「以下を順に入力」「①」「②」「③」のように読みやすく記載する
> - 表現は実務向け・簡潔・具体的にする
> - 「期待される正解例」は要約的でもよいが、実際の回答イメージが分かるようにする
> - 「NG回答例」は、無応答、意図ズレ、抽象すぎる、同じ説明の繰り返し、過剰断言、勝手な前提追加などを適切に含める
> - 教育エージェントとして最も重要なのは「対話継続テスト」であることを踏まえて、内容をやや厚めにしてよい
> # 品質観点
> 特に以下を評価できるように設計すること
> - 応答できるか
> - 日本語として自然か
> - 同じ意図を一貫して理解できるか
> - やさしく、構造的に説明できるか
> - 相手の理解度に応じて説明を変えられるか
> - 曖昧入力で暴走しないか
> - 実務活用に耐えるか
> - 無理な要求に対して適切に期待値調整できるか
> それでは、上記条件に従って、完成版の試験項目表を出力してください。
> ~~~
